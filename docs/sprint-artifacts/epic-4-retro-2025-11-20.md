### 3. Multi-Layer Validation Pattern

**Observation:** The team implemented validation at three layers consistently:

**Pattern:**
1. **UI Layer:** Client-side validation (faster feedback)
2. **Service Layer:** Business logic validation (enforcement)
3. **Database Layer:** Constraints (last-line defense)

**Examples:**
- VAT sum validation: UI checks, Service blocks if >1,000₫ tolerance, DB constraints prevent negative VAT
- Overpayment prevention: UI shows remaining balance, Service enforces, DB constraints prevent negative balances
- RBAC enforcement: UI hides actions, Service validates permissions (@PreAuthorize), DB prevents unauthorized data access

**Impact:** Multi-layer validation caught errors early and prevented data corruption.

**Lesson:** "Never rely on a single validation layer. Defense in depth works."

## Challenges and Growth Areas

### 1. 🔴 Audit Logging Integration Issues (3 stories: 4-1, 4-6, 4-7)

**Issue:** Multiple stories initially used standard logger instead of AuditService.

**Root Cause:** Audit logging wasn't established as a first-class requirement. Developers defaulted to familiar logging patterns.

**Impact:** 
- 2-3 review cycles across 3 stories to fix
- Stories 4-6 and 4-7 had to rework after discovering the pattern in 4-1

**Resolution:**
- ✅ Story 4-6 established proper AuditService method pattern
- ✅ Story 4-7 leveraged the pattern immediately
- ✅ Action item: Document reusable AuditService methods for Epic 5

**Lesson Learned:** "Audit logging must be baked into technical requirements from day 1, not discovered mid-epic."

---

### 2. 🔴 Critical Logic Errors (2 stories: 4-4, 4-1)

**Issue:** Subtle calculation errors slipped through initial development.

**Examples:**
- **Story 4-4 (Aging Report):** daysDiff calculation was inverted (comparing negative instead of positive values)
- **Story 4-1 (VAT Validation):** VAT validation hardcoded to ZERO instead of using actual bill VAT

**Root Cause:** 
- Limited edge case testing during development
- Code review didn't catch inverted logic
- Tests discovered issues during integration

**Impact:**
- Aging report bucketing incorrect
- VAT validation not actually validating
- Both required rework and test cycles

**Resolution:**
- ✅ Test-driven development caught errors before production
- ✅ Added comprehensive edge case tests
- ✅ Code review focused on calculation logic

**Lesson Learned:** "For calculation-heavy features, write tests BEFORE implementation. Edge cases matter."

---

### 3. 🔴 Incomplete Export Implementations (2 stories: 4-4, 4-5)

**Issue:** Export features partially implemented (only one format tested).

**Examples:**
- **Story 4-4:** PDF export thrown exception; Excel worked fine
- **Story 4-5:** Export history not being saved

**Root Cause:**
- Acceptance criteria didn't explicitly require both PDF AND Excel
- Testing focused on "happy path" only
- Edge cases (large datasets, special characters) not tested

**Impact:**
- Users couldn't export aging reports as PDF
- Statement history export functionality broken
- 1-2 review cycles to fix

**Resolution:**
- ✅ Added explicit "test all export paths" to acceptance criteria
- ✅ Created comprehensive export test matrix
- ✅ Both formats now tested in all export stories

**Lesson Learned:** "Test all export paths explicitly. Don't assume if one format works, the other does."

---

### 4. 🔴 Hardcoded Configuration Values (2 stories: 4-3, 4-6)

**Issue:** Account IDs, VAT rates, approval thresholds hardcoded in code.

**Examples:**
- **Story 4-3:** Bank account ID hardcoded (breaks for 2nd company)
- **Story 4-6:** VAT account 3331, VAT rate defaults hardcoded
- **Story 4-2:** Approval threshold (20M VND) hardcoded
- **Story 4-1:** VAT rate default (10%) hardcoded

**Root Cause:** Multi-tenant awareness not consistently applied. Developers saw "this works for the demo company" and shipped it.

**Impact:**
- 🚨 CRITICAL: Second company's bills post to wrong accounts
- 🚨 CRITICAL: VAT calculations incorrect for companies with different rates
- Violates multi-tenancy architectural requirement
- Requires Preparation Sprint fixes before Epic 5

**Resolution:**
- ✅ Identified all hardcoded values
- ✅ Scheduled 4-day Preparation Sprint to migrate to CompanySettings
- ✅ Will implement database-driven configuration before Epic 5 starts

**Lesson Learned:** "In multi-tenant systems, EVERY configuration must be database-driven, never hardcoded. Add this to pre-review checklist."

---

### 5. 🔴 Frontend-Backend Integration Mismatches (2 stories: 4-5, 4-6)

**Issue:** Frontend and backend had different assumptions about API contracts.

**Examples:**
- **Story 4-5:** FE expected bill history in nested structure; BE returned flat array
- **Story 4-6:** FE sent VAT data one way; BE parsed it differently

**Root Cause:** 
- No API contract definition before development started
- No shared mocks or contract-first specifications
- Integration happened late in development cycle

**Impact:**
- Data parsing failures during integration
- 1-2 additional review cycles to align
- Delayed feature completion

**Resolution:**
- ✅ Created explicit API contract documentation
- ✅ Used OpenAPI/Swagger for future specifications
- ✅ Developed shared API mocks for parallel development

**Lesson Learned:** "Define API contracts BEFORE implementation, not after. Use contract-first development for parallel FE/BE work."

### 3. Multi-Layer Validation Prevents Disasters

**Finding:** Errors that slipped through one layer were caught by another.

**Examples:**
- VAT ratio validation: UI didn't catch negative VAT, but Service layer did
- Overpayment prevention: FE UI could be bypassed, but Service enforced it
- RBAC: UI could be spoofed, but Service validation blocked unauthorized access

**Implication:** No single layer is sufficient. Defense in depth is essential in financial systems.

**Recommendation:** For any critical feature, implement validation at UI, Service, and Database layers.

**Critical Items:**

**Implication:** Hardcoded values are a critical bug in multi-tenant systems, not just a refactoring task.

**Recommendation:** Create "Multi-Tenancy Checklist" to verify all configuration is database-driven before story approval.
